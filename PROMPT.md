# Задание для агента: приложение для отслеживания дедлайнов

С нуля разработай полноценное веб-приложение для отслеживания дедлайнов. Реализуй приложение, проведи проверки и запусти его локально через Docker Compose. Не ограничивайся планом или макетом.

## Правила работы

- Работай в текущей папке проекта.
- Не инициализируй Git, не создавай коммиты и не выполняй git push.
- Не создавай дополнительные документы, отчёты и планы без прямой просьбы. О результате сообщи в чате.
- Перед завершением удали временные и тестовые файлы, созданные тобой в ходе задачи. Не удаляй существовавшие до начала работы тесты. Результаты проверок сохрани в сообщении пользователю.
- Самостоятельно принимай обычные технические решения и доведи работу до работающего локального приложения.

## Исходные данные

Приложение предназначено для планирования подготовки и размещения медицинских материалов и e-mail-рассылок. Основа — предоставленный скриншот таблицы. Импорт Excel пока не требуется. Не пытайся переносить изображение таблицы целиком: реализуй её данные и рабочие сценарии.

На скриншоте есть разделы «База Медзнат», «Отправки Medpoint» и «Отправки Onpoint», внутри первого раздела — месяцы. Каждая строка соответствует отдельному размещению или отправке. Один материал может встречаться на нескольких площадках с разными датами, специальностями, хедерами, прехедерами и статусами. Не объединяй такие строки в одну задачу и не запрещай повторяющиеся темы.

Запись содержит:

- Площадка/раздел — обязательный select из справочника: «База Медзнат», «Отправки Medpoint», «Отправки Onpoint».
- Срок загрузки в Mhub+ — основной дедлайн; обязательная дата с возможностью уточнить время. По нему определяются срочность, основная сортировка и уведомления.
- Дата (e-mail) — отдельная необязательная календарная дата отправки/публикации. Это не адрес электронной почты и не основной дедлайн.
- Специальность — необязательный select из справочника, исходные значения «Gastro» и «GP».
- Материал/проект — необязательное текстовое поле. Это столбец без заголовка между специальностью и темой: на скриншоте в нём указаны названия материалов, например «Тегопразан Эрозивная ГЭРБ» и «Тегопрекс — баннеры». Название поля является рабочей интерпретацией скриншота.
- Тема — обязательное многострочное поле, используемое также как название записи. Например: «ШР_1: Эрозивная ГЭРБ: как повысить вероятность заживления» или «БАННЕР».
- Хедер — необязательное многострочное поле.
- Прехедер — необязательное многострочное поле.
- Комментарий — необязательное многострочное поле.
- Ответственный — необязательное текстовое поле, дополнительное к исходной таблице.
- Статус — необязательный select из управляемого справочника; пустое значение отображай как «Не задан». Не создавай под него фиктивный статус в базе.
- Выполнено — отдельный булевый признак с датой выполнения. Пользователь может отметить и снять выполнение независимо от рабочего статуса.
- Дату создания и дату последнего изменения.

Месяц для группировки вычисляй по дате e-mail, а если она отсутствует — по основному дедлайну. Учитывай год: январь разных лет — разные группы. Серые строки с названиями месяцев на скриншоте являются заголовками групп, а не записями. Объединённые ячейки не воспроизводи: каждая запись хранит собственные значения полей.

Дата e-mail может отсутствовать или отличаться от срока загрузки. Если она раньше основного дедлайна, показывай предупреждение, но разрешай сохранение. Не подставляй текущий год молча для дат со скриншота без года. Для демонстрационных записей используй явно заданные даты относительно текущего момента.

## Статусы и справочники

Первоначальные варианты статуса, в порядке со второго скриншота:

1. Пишем
2. На согласовании
3. Дорабатываем
4. Загружено DROID
5. Mhub
6. Дизайн
7. Согласовано БМ
8. Ждем размещение МЗ
9. Корректор

В первой таблице также встречаются «Размещение МЗ» и «Загружено». Это примеры значений из исходных данных: не добавляй их в первоначальный набор автоматически и не сопоставляй молча с другими статусами. Пользователь сможет добавить их самостоятельно.

Реализуй в интерфейсе управление справочниками статусов, площадок и специальностей:

- Добавление нового значения без изменения кода и перезапуска приложения.
- Переименование и изменение порядка отображения.
- Для статусов — выбор цвета бейджа. Исходные цвета приблизь ко второму скриншоту с адаптацией к тёмной теме.
- Архивация значения: оно сохраняется в существующих записях, но недоступно для нового выбора. Восстановление из архива.
- Запрет пустых названий и дубликатов с учётом регистра и пробелов по краям.
- Хранение справочников в PostgreSQL и ссылки по стабильным ID; переименование не должно разрывать связи.
- Идемпотентное начальное заполнение: не восстанавливай при перезапуске переименованные или архивированные значения и не создавай дубликаты.

Цвет рабочего статуса и цвет срочности — разные признаки. Ни один из исходных статусов автоматически не означает выполнение. Зелёное оформление выполненной записи определяется только пользовательской отметкой «Выполнено»; рабочий статус при этом сохраняется.

## Возможности

- Создание, просмотр, редактирование и удаление записей с подтверждением удаления.
- Изменение статуса через select и отметка «Выполнено», доступные прямо в списке.
- Поиск по теме, материалу/проекту, хедеру, прехедеру, комментарию и ответственному.
- Фильтры по площадке, специальности, статусу (включая «Не задан»), выполнению, месяцу/году и срочности, включая просроченные записи.
- Два режима списка: общий список с глобальной сортировкой по дедлайну и группировка по площадке и месяцу. В режиме группировки сортируй записи внутри групп. Предусмотри дополнительную сортировку по дате e-mail; отсутствующие даты помещай в конец.
- Сортировка по дедлайну: сначала ближайшие, с возможностью переключить порядок. По умолчанию незавершённые записи идут первыми, выполненные — в конце; внутри групп соблюдается выбранная сортировка. Просроченные незавершённые записи при сортировке по возрастанию идут перед будущими.
- Счётчики: всего, просрочено, дедлайн меньше недели, выполнено. Счётчик «меньше недели» учитывает только будущие незавершённые записи.
- Сохранение данных в базе, включая сохранность после перезапуска контейнеров.
- Корректные пустые состояния, загрузка, сообщения об ошибках и валидация форм.

## Правила срочности и цветов

Вычисляй оставшееся время относительно текущего момента. Неделя — ровно 7 × 24 часа. Используй одинаковую логику на клиенте и сервере:

1. Установлена отметка «Выполнено» — зелёный независимо от дедлайна; это правило имеет высший приоритет.
2. Просроченная незавершённая запись — красный и явная подпись «Просрочено».
3. До дедлайна меньше 7 суток — красный.
4. От 7 до 14 суток включительно — жёлтый.
5. Больше 14 суток — нейтральный.

Ровно в момент дедлайна незавершённая запись считается просроченной. Дополняй цвет текстовой меткой, чтобы срочность была понятна без различения цветов. Показывай сам дедлайн и понятную подпись оставшегося времени. Обновляй срочность автоматически без перезагрузки страницы.

Основной дедлайн храни как UTC timestamp, ввод и отображение выполняй в локальном часовом поясе браузера. Явно показывай используемый часовой пояс рядом с полем дедлайна. Если пользователь вводит только дату загрузки, устанавливай время 23:59 этой даты в часовом поясе ввода и показывай это в форме до сохранения. Дату e-mail храни как PostgreSQL DATE без преобразований часового пояса. Сохранённый момент дедлайна не должен меняться при открытии приложения из другого часового пояса.

## Тестовые уведомления

Реализуй серверную периодическую проверку дедлайнов, работающую и при закрытом браузере. Пока уведомления выводятся только в stdout сервера и доступны через `docker compose logs`.

- Проверяй записи при запуске сервера и далее каждую минуту.
- Для незавершённых записей отправляй уведомления при попадании в интервалы: от 7 до 14 суток, меньше 7 суток и просрочено. Для дедлайна дальше 14 суток уведомление не требуется.
- При создании записи или изменении дедлайна проверяй актуальную срочность сразу. Если запись сразу попала в срочный интервал, отправляй одно уведомление о текущем интервале, без уведомлений о пропущенных интервалах.
- Выводи структурированный лог с типом события, ID записи, темой, площадкой, дедлайном, статусом и срочностью. Ошибки доставки логируй отдельно.
- Не дублируй уведомление об одном интервале для одной записи при каждой проверке и после перезапуска сервера: сохраняй состояние уведомлений в базе.
- Изменение дедлайна начинает новый цикл уведомлений. Установка отметки «Выполнено» отключает уведомления. Снятие отметки начинает новый цикл с одной проверкой текущего интервала. Изменение рабочего статуса не сбрасывает цикл.
- Раздели определение события и его доставку через небольшой интерфейс уведомлений. Сейчас реализуй консольный адаптер; впоследствии к нему можно будет подключить Telegram. Сам Telegram, токены и сетевые интеграции сейчас не добавляй.

## Дизайн

Самостоятельно разработай аккуратный современный интерфейс в тёмных тонах. Интерфейс полностью на русском языке.

- Графитовый фон, немного более светлые поверхности, тонкие границы, читаемая типографика и спокойный акцентный цвет.
- Срочность показывай отдельной меткой и умеренным акцентом строки. Рабочий статус показывай отдельным цветным бейджем с названием; цвет бейджа не должен подменять индикацию дедлайна. Обеспечь достаточный контраст.
- Основной экран: заголовок, кнопка добавления, счётчики, поиск и фильтры, переключатель группировки, список записей и доступ к управлению справочниками.
- Основное представление — вертикальный список широких карточек-плашек, по одной записи на всю доступную ширину контейнера. Не используй таблицу, общую строку заголовков столбцов или сетку из нескольких карточек в ряд.
- В каждой плашке сразу показывай всю информацию записи: тему, площадку, специальность, материал/проект, срок загрузки, дату e-mail, хедер, прехедер, комментарий, ответственного, рабочий статус, отметку выполнения, срочность, даты создания и изменения, а для выполненных — дату выполнения. Пустые необязательные поля обозначай «Не указано».
- Организуй поля внутри плашки по смыслу: тема и срочность в верхней части, даты и атрибуты компактными блоками с подписями, длинные тексты отдельными читаемыми блоками, действия и select статуса в удобной зоне. Используй свободную компоновку, а не выравнивание полей всех записей в общие табличные колонки.
- Показывай тексты полностью с переносами строк; не скрывай информацию за многоточием, наведением, раскрытием карточки или переходом на отдельный экран. Высота плашки зависит от объёма содержимого.
- На мобильном сохраняй тот же список плашек со всеми полями; внутренние блоки перестраивай в одну колонку без горизонтального скролла. Заголовки групп по площадке и месяцу размещай между плашками.
- Форму создания и редактирования покажи в модальном окне или боковой панели.
- Предусмотри управление с клавиатуры, видимый фокус, подписи полей и корректный фокус в модальных окнах.
- Не используй заглушки вместо работающих действий.

## Техническая реализация и Docker

Обязательный стек:

- Фронтенд: React + Vite + TypeScript.
- Бэкенд: Go с REST API; периодические проверки уведомлений выполняются на бэкенде.
- База данных: PostgreSQL.

Остальные библиотеки и технические решения выбирай самостоятельно, отдавая предпочтение простоте и поддерживаемости. Авторизация и многопользовательский режим для локального прототипа не требуются.

- Реализуй серверную валидацию и понятные ошибки API.
- Добавь необходимые миграции или воспроизводимую инициализацию схемы базы.
- Подготовь Dockerfile для фронтенда и бэкенда, `.dockerignore` и `compose.yaml` с сервисами frontend, backend и postgres; используй постоянный volume для PostgreSQL. Собранный Vite-фронтенд отдавай через веб-сервер с проксированием `/api` на Go-бэкенд; браузер должен обращаться к приложению и API через один origin.
- Запуск должен выполняться командой `docker compose up --build -d` без ручной установки зависимостей на хосте.
- Предусмотри healthcheck, ожидание готовности PostgreSQL перед миграциями и запуском бэкенда, запуск периодических проверок и автоматическое восстановление процесса при сбое. Порты PostgreSQL и бэкенда не публикуй на хост без необходимости; соединение между сервисами выполняй через внутреннюю сеть Compose.
- Публикуй приложение только на localhost. Предпочтительный адрес — `http://localhost:3000`; если порт занят, используй свободный и укажи фактический адрес.
- При необходимости добавь небольшой набор демонстрационных записей, покрывающих все категории срочности и статусы. Их создание должно быть явным и идемпотентным; перезапуск не должен размножать или восстанавливать удалённые пользователем данные.

## Проверки и завершение

Проверь фактическую реализацию, исправь найденные проблемы и повтори затронутые проверки:

- Сборка, проверка типов и линтер, если предусмотрен стеком.
- Создание, редактирование, удаление, смена статуса, независимая отметка выполнения, поиск, фильтрация и оба направления сортировки.
- Добавление, переименование, изменение порядка, архивация и восстановление значений справочников; сохранение связей записей и отсутствие дублей после перезапуска.
- Независимость цвета рабочего статуса от срочности, пустой статус, повторяющиеся темы на разных площадках, группировка по месяцу и году, отсутствующая дата e-mail, ввод дедлайна без времени и корректная обработка часовых поясов.
- Границы цветов: просрочено, ровно дедлайн, чуть меньше 7 суток, ровно 7 суток, ровно 14 суток, больше 14 суток; зелёный цвет выполненной записи при любом дедлайне.
- Уведомления: текущий интервал, переходы между интервалами, отсутствие дублей, перезапуск, смена дедлайна, завершение и повторное открытие записи.
- Сохранность данных и состояния уведомлений после перезапуска контейнеров.
- Фактический запуск Docker Compose, healthcheck, HTTP-доступность и отсутствие ошибок в логах.
- Если доступен браузерный инструмент, проверь основной пользовательский сценарий и мобильную компоновку в браузере. Если недоступен, честно укажи ограничение.
- Проверь, что список представлен широкими плашками, все поля доступны сразу, длинные тексты отображаются полностью и не вызывают наложений или горизонтального скролла на мобильном.

Не заявляй об успешной проверке без её выполнения. Если Docker недоступен, выполни все доступные проверки и укажи конкретную причину, по которой локальный запуск не состоялся.

После очистки созданных временных и тестовых файлов оставь приложение запущенным через Docker.
